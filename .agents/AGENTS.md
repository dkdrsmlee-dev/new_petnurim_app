# 프로젝트 규칙 (Project Rules)

## Git 커밋 및 푸시 제약 사항
- **중요**: 사용자가 명시적으로 승인(예: "커밋 푸시")을 하기 전까지는 절대 변경 사항을 커밋하거나 원격 저장소(`origin`, `doctor`)에 푸시하지 않습니다.
- 모든 코드 작업은 로컬 변경 상태로 대기하며, 사용자에게 작업 완료 요약 보고 후 승인을 받아 진행합니다.
- 부득이한 경우를 제외하고 커밋 메시지는 반드시 **한글**로 작성합니다.

## 백엔드 API 참고 제약 사항
- 백엔드 API 관련 스펙(요청/응답 파라미터, 엔드포인트)은 사용자가 별도의 JSON 파일이나 설명을 업로드하지 않더라도 개발 서버(`http://api-dev.petnurim.kr/api-test-json`, 구 주소 `http://192.168.0.147:4011/api-test-json`)를 통해 획득하여 `/Users/smlee/.gemini/antigravity-cli/brain/51274b79-905c-46e8-8b93-f66226b3b76e/scratch/openapi_spec.json`에 저장된 OpenAPI 스펙을 직접 참고하여 구현합니다.
- 앱이 호출하는 백엔드 API 베이스 URL은 `http://api-dev.petnurim.kr` 입니다(구 주소 `http://192.168.0.147:4011`, HTTP 전용). `lib/core/config/app_config.dart`의 `NURIM_API_BASE_URL` 기본값으로 관리합니다.

## 피그마 디자인 분석 제약 사항
- 피그마 MCP를 사용하여 디자인 분석을 진행할 때, 메인 레이어만 확인하는 것에 그치지 않고 반드시 하위 레이어(Sub-layers)의 세부 속성(폰트 스타일, 색상 값, 마진, 패딩, 정렬 등)까지 딥 인스펙트(Deep Inspect)하여 디테일하게 분석 및 구현합니다.
## 코드 수정 및 구현 전 계획 보고 및 승인 제약 사항
- **중요**: 코드를 실제로 수정(작성/편집)하기 전에 반드시 상세한 수정 계획(수정 대상 파일, 수정 예정 코드 조각, 동작 변경 흐름 등)을 작성하여 사용자에게 보고하고, 사용자의 명시적인 승인을 얻은 후에만 파일 수정 작업을 시작합니다.

## README.md 문서화 동기화 제약 사항
- 카카오 앱 키 변경이나 실행 설정 정보 등 주요 구동 환경 변수가 바뀔 때는 관련 웹 콘솔 플랫폼 등록 값 및 설정 가이드를 `README.md`에 반드시 적절하게 기록하고 동시 커밋 및 푸시를 수행합니다.
- 단순 키 변경뿐만 아니라 프로젝트의 주요 아키텍처 변경, 새로운 핵심 비즈니스 로직(예: 배너 롤링, 대표 펫 지정 등) 구현 및 동작 사양 변경 등 프로젝트의 중요 정보라고 판단되는 모든 내역은 `README.md`에 즉시 기록/보완하여 함께 커밋 및 푸시를 수행합니다.

## 작업 승인 및 커밋/푸시 승인 단계 분리 제약 사항
- 구현 완료 요약 보고에 대한 승인 단계와, 최종 커밋 및 원격 리포지토리 푸시 승인 단계는 절대로 한 번에 일괄 처리하지 않으며 반드시 개별 단계로 분리하여 진행합니다.

## 에이전트 규칙 자동 기록 지침 (Meta-rule)
- 사용자가 프로젝트의 개발 방식, 제약 사항, 환경 가이드 등 규칙성 지시를 내릴 경우, 사용자가 명시적으로 "AGENTS.md에 기록해라"라고 언급하지 않더라도 에이전트가 알아서 판단하여 즉시 `.agents/AGENTS.md` 파일에 해당 행동 지침을 기록/보완합니다.

## 화면 캡처 자동 조회 및 분석 제약 사항
- 사용자가 "캡처 확인"이라는 명시적 지시를 하면, 별도의 파일 경로가 메시지에 첨부되어 있지 않더라도 즉시 `/Users/smlee/Documents` 디렉토리를 탐색합니다.
- `스캔 대상 명칭`: 파일 이름이 `스크린샷 202X-XX-XX 오전/오후 X.XX.XX.png` 형식이 아니더라도, 해당 디렉토리(`/Users/smlee/Documents`) 내부에서 **가장 최근에 생성된 최신 PNG 이미지 파일**을 추적해 직접 조회(`view_file`)한 뒤 분석 결과를 기반으로 질문에 답변합니다.
## 공통 위젯 재사용 및 신규 공통 위젯 개발 보고 제약 사항
- UI를 설계 및 구현할 때는 프로젝트 내 공통 위젯 폴더(예: `lib/core/widgets/` 등)에 이미 구현되어 있거나 매우 유사한 위젯이 있는지 최우선적으로 탐색하여 활용(재사용)합니다.
- 만약 기존 공통 위젯 중 적합한 것이 없어 새로 설계해야 할 때, 해당 요소를 공통 위젯으로 추상화하여 구현하는 것이 향후 유지보수 측면에서 유용하다고 판단될 경우 개발에 착수하기 전 사용자에게 세부 디자인 계획을 포함하여 사전 보고합니다.
